1. Purpose & scope

Why this document exists

This playbook documents the Registrar workflow as it is actually implemented in the codebase — every step below is traced to a route, controller method, or validation rule in routes/web.php and app/Http/Controllers/Registrar/. It is written for onboarding a new Registrar-office staff member and for use as a reference during audits or handovers.

The Registrar is the operational center of the system: it is the only role that can stand up academic structure (programs, curricula, sections), move a person from Applicant to Student, run the grading approval chain to completion, and open or close an academic term. Every other role — Student, Faculty, Parent, Applicant — depends on decisions made in this module.

2. Roles & access

Who else is in the system, and how access is enforced

Every login account carries a single module value that determines its portal. The Registrar module is functionally the administrator role: routes named registrar.* accept both the registrar and admin module values.

Role (module)PortalRelationship to Registrar
registrarRegistrar dashboardOwns academic structure, enrollment, grading sign-off, term lifecycle, and system configuration.
facultyFaculty portalSubmits grades and attendance into records the Registrar reviews and finalizes.
studentStudent portalCreated by the Registrar (directly or via applicant conversion); views records the Registrar maintains.
applicantApplicant portalPre-student stage; the Registrar reviews and converts applicants into students.
parentParent portalRead-only view of a linked student's records.

Beyond the module gate, every Registrar screen is checked a second time by a fine-grained permission engine (app/Support/UserAccessGate.php): each route maps to a module code (e.g. academics_subject_file) and each HTTP verb maps to a permission type — view / create / edit / delete. Access can be tuned per user or per custom role from inside the system itself, under Admin Tools → Access Management.

Where to configure it

Roles: registrar.admin-tools.access-management.roles  ·  Per-user overrides: registrar.admin-tools.access-management.user-accounts

3. Getting in

Login, and the forced password reset every new account hits

ItemValue
Login URL/login/registrar
Landing pageAuto-redirects to registrar.dashboard on success
Auth checkUsername + password, then confirms module = registrar and a linked registrar_id exists — an unlinked account is signed back out with an "account not linked" error

Any account created by the Registrar (new staff, or a student produced by applicant conversion) is issued with force_password_reset = true. On next login the system intercepts every request and redirects to /password/setup until a new password is set — this is a global middleware, not a per-screen check, so it cannot be bypassed by deep-linking.

4. Day-one critical path

The minimum end-to-end sequence to take the system from empty to "a student can be graded"

This is the direct answer to "what is the first thing that needs to happen, end to end, to use the system". It is the shortest path through Phases A–D that is not skippable — each step is a hard dependency (foreign key or explicit validation) for the one after it. Everything in Phases E–G repeats every term; the steps below happen once per environment (1–8) and once per term (9–13).

  1. Configure the academic calendar basics
    School year / semester config, grade-posting windows, document signatories. Screen: registrar.admin-tools.system-config.*.
  2. Create Departments
    A Program cannot exist without one. Screen: academic-master.program-file (department panel).
  3. Create at least one Program (Course)
    saveProgramSetup validates a unique program code and a real department_id. This is the root of everything academic.
  4. Build the Subject catalog
    Screen: academic-master.subject-file. These are master records — the raw pool a curriculum draws from.
  5. Build a Curriculum for the Program
    saveCurriculumSetup rejects the request outright if the Program or any selected Subject doesn't already exist.
  6. Route the Curriculum to Published status
    Department head → Dean → Registrar → Academic Council approval, then is_published = true. Nothing downstream can start without this flag.
  7. Add Rooms
    Screen: scheduling.room-file. Needed before schedules can be auto-generated.
  8. Create staff / faculty accounts
    Screen: faculty-mgmt.faculty-create. Needed before a section can be assigned a teacher.
  9. Open an Academic Term
    openNewAcademicTerm — on a fresh system there is no prior term to close, so this is the one exception to the "must close current term first" rule.
  10. Create Section Offerings
    storeSectionOffering pulls its subject list straight from the published curriculum from step 6 — this is where that dependency is enforced in code, with an explicit rejection message if it isn't met.
  11. Prepare the Class Schedule and assign Rooms/Teachers
    Auto-generate, then confirm, time slots, rooms, and faculty per section-subject.
  12. Enroll Students
    Either directly via storeStudent, or by admitting Applicants first (Phase C) and bulk-converting them. Each new student gets a linked login account automatically.
  13. System is now live for the term
    Faculty can take attendance and submit grades; the Grading Sheet approval chain (Phase F) becomes active.

Phases A and B are effectively one-time setup (repeated only when a new program is introduced). Phases C through G repeat every academic term, and G feeds back into D to start the next cycle.

Why this comes first

The grading configuration here is what the Phase F approval chain and every transcript/report in Phase G reads from. Setting it up after grades exist means retroactively re-scoring records — configure it once, before the first term opens.

What conversion actually does

bulkConvertToStudent generates a student number, copies name/sex/age and preferred course from the applicant's application, creates a linked User login with an auto-generated PLP email and a temporary password, and flags the account for forced reset — inside a single database transaction. This is the formal hand-off point from the Applicant domain to the Student domain.

9. Phase D — Term setup & sections

Opens each term and materializes the classes students will actually enroll into

Hard rule — term lifecycle

A new Academic Term can only be opened (openNewAcademicTerm) once the current term's status is Closed. On a fresh install there is nothing to close, so the first term is the only one opened without this precondition.

What enrollment does under the hood

storeStudent auto-generates a student number if left blank, creates the Student record, and creates a linked User account (username = student number, temporary password PLP-{student_no}, forced reset) — all inside one transaction, so a partially-created account can't be left behind.

11. Phase F — Grading approval chain

The Registrar is the final signature, never the first

Grades never move directly from a faculty member to being final. Each subject carries a status field that only advances one step at a time, strictly forward, unless returned:

TaskScreen
Review & act on submitted grades (approve / finalize / reject)faculty-mgmt.grading-sheet
Bulk-import grades from spreadsheet templatefaculty-mgmt.upload-grades
Process grade correction requestsstudent-mgmt.academic-record (correction approve/reject)
Track deficiencies / incompletesservices.grading-academic.deficiency
Direct override (audited, exception path)admin-tools.grade-override
Use sparingly

Grade Override bypasses the Faculty → Dean → Registrar chain entirely. It writes to its own audit log and should be reserved for correcting genuine errors after the fact, not for routine grading.

Hard rule — closing a term

closeCurrentSemester runs a validation pass (academicTermCloseValidationIssues()) before it will set the term to Closed — outstanding items (e.g. incomplete grading) block the close. Every closure and re-open is written to the audit trail via AuditTrailRecorder.

Once Closed, the term can be re-opened into the next cycle (back to Phase D) — optionally using Academic Setup Automation and Promotion Readiness to auto-generate the next term's sections and student year-level movements from the closed term's data, rather than rebuilding Phase D by hand.

14. Glossary

TermMeaning in this system
ProgramAn academic degree/course offering (model: Course), e.g. BSCS. Belongs to a Department.
CurriculumA versioned subject plan for a Program and school year (CourseCurriculum). Must pass a four-stage approval chain and be published before it can be used.
Subject (catalog)A master catalog record — code, name, units — that a Curriculum draws from.
Subject (section instance)The same underlying table, reused: once a Section Offering is created, one row per curriculum subject is generated to represent the actual class being taught that term.
Section OfferingA specific class group (e.g. "BSCS 1-A") for a Program / year level / term, generated from a published Curriculum.
Academic TermA school year + semester with a lifecycle status: Draft → active → Closed → Archived.
Grading status chainPer-subject status on the grading approval workflow: SUBMITTED → DEAN_APPROVED → REGISTRAR_FINALIZED, or returned to Faculty via a rejection.
ApplicantA pre-student record from the admissions pipeline; becomes a Student via bulk conversion.
