1. Purpose & audience

Why this guide exists

This is a User Acceptance Test script: every menu item the Registrar role can open, listed with the exact steps to run it and the result that means it's working. It is run by the people who will actually use the system day to day — the Registrar, Assistant Registrars, College Secretaries, and Front-Desk Officers — not by developers, so a screen only counts as "accepted" once an end user has clicked through it themselves and confirmed the result matches what their job needs.

It pairs with the Registrar Flow business process guide, which explains how these screens fit together term over term. This document exists to confirm, one by one, that each of them actually works. For a shorter run through just the core pipeline — system configuration through a posted grade, no documents or reports — see the Config to Grade UAT.

2. How this UAT is organized

Build order, not menu order — each day depends on data the last one created

The sidebar groups screens by topic, but topic order isn't build order: Student List and Enrollment List are meaningless on an empty system, because a student can't be enrolled into a program that has no curriculum, into a section that has no room, in a term that hasn't been opened. So this script runs in the same dependency order the system itself enforces — the same order the Registrar Flow guide's Day-one checklist lays out: system and curriculum setup first, then rooms/faculty/scheduling, then students and enrollment, then grading, and only then the certificates and reports that read all of it back. Nothing in a later day can be tested honestly until every case in the days before it passes.

Scoring convention

Mark Fail the moment the actual result doesn't match what's written, not just when the page errors out. Log a one-line note of what actually happened in the Remarks column, then re-test the same row after a fix ships — don't overwrite the original Fail. A day is considered accepted only once every row in it reads Pass, since every later day builds its test data on top of it.

How to run every process

Each test case below is a true click-by-click walkthrough: every menu level is its own numbered step, followed by the action, page confirmation, and final result verification. The separate Expected Result column states what must happen, while Image Result focuses on the main content or output area instead of the sidebar navigation. Complete all steps in order before marking Pass or Fail; select a thumbnail to open the complete screenshot.

1. PrepareConfirm the prerequisite and use the same shared UAT record throughout the day.
2. FollowComplete each click-by-click numbered step, including every level of the menu path.
3. UnderstandRead the short explanation under a step whenever its purpose is not obvious.
4. VerifyCompare your saved data with every written expected result and capture evidence.
5. Compare imageUse the separate Image Result thumbnail to confirm you reached the same screen or output area.

3. Coverage map

Five days, one build order, closing in sign-off

Day 1 creates the programs, curricula, and grading rules nothing else can exist without. Day 2 turns that into rooms, faculty, and an actual class schedule. Only then, on Day 3, does adding and enrolling a student mean anything. Day 4 grades what Day 3 enrolled, and Day 5 prints, reports, and administers everything the first four days built.

4. Access & navigation

Start every training day from the same known point

  1. Open the PLP portal.Use the approved Test or Production URL supplied by MIS. Complete UAT in Test unless the facilitator says otherwise.
  2. Select the Registrar module.Confirm the heading reads Registrar Login before entering credentials.
  3. Sign in with your assigned account.Never share a password or use another tester's account; the Audit Trail must identify the person who performed each action.
  4. Check the dashboard and current term.Verify your name, role, active school year, semester, and notification count before opening a module.
  5. Use the left navigation.Follow the exact menu path shown in each test case, then confirm the page title before creating or changing data.
Stop before testing

If your role, school year, semester, or available menu does not match the facilitator's test sheet, sign out and report the mismatch. Do not continue in the wrong term.

5. Day 1 — System & Academic Structure Setup

15 test cases · the programs, curricula, and rules nothing else can exist without

Why this is Day 1

Nothing downstream works on an empty system. A section can't be created without a published curriculum; a curriculum can't be built without a Program and a Course File; grades can't post without a grading scale and a transmutation table. This day exists so every day after it has real, correct data to test against — not placeholders.

Day 1 walkthrough

Create the academic foundation

  1. Confirm system settings.Open signatories, school term, access, and grading configuration.
  2. Build the structure.Create the college, program, course file, and curriculum in dependency order.
  3. Validate before publishing.Check subjects, units, prerequisites, grade rules, then publish the curriculum.

6. Day 2 — Resources, Term & Class Scheduling

15 test cases · turning Day 1's curriculum into an actual, bookable class schedule

Why this is Day 2

A section needs a room and a teacher before it can hold a class, and it needs an open term before it can exist at all. This day builds every physical and human resource, opens the term, and produces the class schedule — the last thing that has to exist before a student can be enrolled in anything.

Day 2 walkthrough

Turn the curriculum into classes

  1. Add resources.Create or verify faculty, buildings, hallways, rooms, and room-subject rules.
  2. Open the term.Set the school year, semester, grading periods, and enrollment window.
  3. Schedule and conflict-check.Create sections, assign subjects, rooms, and faculty, then resolve every overlap.

7. Day 3 — Students, Enrollment & Classroom Operations

13 test cases · the first day a student can actually exist in the system

Why this is Day 3, not Day 1

This is the earliest point in the week where adding a student means anything: there's a published curriculum to enroll them under, a section with a room and a teacher to enroll them into, and an open term to enroll them in. Testing Student Records before this point would only prove the search box works, not that enrollment does.

Day 3 walkthrough

Create and enroll the test student

  1. Create the student record.Complete identity, contact, program, and requirement information.
  2. Enroll into the open term.Select the correct curriculum, year level, section, and eligible subjects.
  3. Verify every downstream list.Confirm the student appears in Enrollment List, Class List, and the assigned faculty view.

8. Day 4 — Grading & Academic Records

15 test cases · turning Day 3's enrollment into official, printable grades

Why this is Day 4

Grades can only be encoded for a student who's enrolled in a class — Day 3's work — against the scale and transmutation table Day 1 configured. Everything in Day 5 (transcripts, certificates, honor rolls) reads the numbers this day produces, so a Fail here should block Day 5 from starting on that student's record.

Day 4 walkthrough

Post grades and verify records

  1. Encode the test grades.Use the assigned class list and the correct grading period.
  2. Review the computation.Compare raw scores, transmuted grade, remarks, units, and GWA before posting.
  3. Read the official outputs.Confirm posted values match the grade file, COG, report card, and certificate previews.

9. Day 5 — Requests, Reports & System

18 test cases · the paperwork and oversight that read back everything built this week

Why this is Day 5

Student requests, reports, and master files are read-only views over what Days 1–4 built — there's nothing left to set up, only to confirm the whole chain reads back correctly. This is also where the week gets audited: Master Files and Audit Trail exist specifically to catch anything the four days before missed.

Day 5 walkthrough

Prove the full record reads back

  1. Process student requests.Open each form with the Day 3 test student and verify all auto-filled fields.
  2. Reconcile reports.Compare GWA, CWA, certifications, and graduation data with Day 4's posted records.
  3. Audit and sign off.Review Master Files and Audit Trail, record every exception, and complete acceptance only after re-tests pass.

10. Sign-off & go-live

What "accepted" means before the office goes live

The Portal is ready for live use once every one of the 76 rows above reads Pass, or every Fail has a linked fix that was re-tested and now reads Pass. Because each day's data feeds the next, a Fail on an earlier day should pause testing on whatever downstream row depends on it rather than being tested against broken data.
